# Loots repository guidance

Loots is the owner's private, hosted platform; each workflow is a module under it. The first shipped module is Profile (formerly Resume): the owner's career details as fields, typed in or imported from a resume chosen in Google Drive (`docs/product/profile-resume.md`). Engineering (formerly Engineering Lab; code, tables and `/api/lab` keep the `engineering-lab` and `lab` names), a learning system for full-stack and AI engineering, is in progress. Do not relate this project to Haven.

## Where things live

- `apps/web`: Next.js UI, API routes, Google OAuth, sessions, and database access.
- `packages/domain`: shared artifact types and format rules.
- `packages/drive`: Google Drive adapter.
- `packages/agents`: the Profile import and rewrite, and the term lookup. Engineering has no OpenAI agents; Claude teaches through the connector.
- `apps/web/src/features/profile/`, `components/profile/` and `app/profile/`: the Profile module. `/` redirects to `/profile`. `pnpm --filter @ken-os/web test:db:profile` checks its store against local Postgres.
- `apps/web/src/features/connector/`, `features/engineering-lab/agent-tools.ts`, `/api/mcp` and `/oauth/authorize`: the Claude connector (`docs/architecture/engineering-claude-first.md`, section 5). Claude reads Engineering, reports progress, and saves exercises and notes; everything it saves is untrusted input, like Terms selections. Claude marks a topic Learned only with the owner's own words as evidence, never changes a status the owner set, never edits or deletes the owner's notes, and no tool records a run, opens a solution, or changes the role or the profile; `agent-tools.test.ts` and `status.test.ts` enforce it. Tools live only in `agent-tools.ts`, which never imports route or MCP code. Claude's exercises run only in the browser runner, after the page checks them. `pnpm --filter @ken-os/web test:db:connector` checks sign-in and `/api/mcp` against local Postgres. The Project's instructions are `docs/product/claude-project-instructions.md`.
- `apps/web/src/features/terms/` and `components/terms/`: Loots-wide term lookup (select text, press Explain or E) and the Terms page. Every page also underlines saved terms in its reading text, the first time each appears, and shows the saved meaning on hover or tap (`saved-term-marks.tsx`, matching in `firstTermMatches`); it paints with the CSS Custom Highlight API and never changes the page's text, and `data-term-skip` opts an area out. Selected text is untrusted data; links must be on the trusted sites in `packages/domain` (`SOURCE_DOMAINS`). `pnpm --filter @ken-os/web test:db:terms` checks it against local Postgres.
- `docs/product/brief.md`: platform-wide scope and acceptance criteria.
- `docs/architecture/engineering-claude-first.md`: source of truth for the Engineering module since 13 Oct 2026: Claude teaches through the connector, and Loots shows the roadmap, topic statuses, Claude's reports and notes on one page. Record later decisions there. `engineering-rebuild.md`, `engineering-claude-connector.md`, `docs/product/ai-engineering-learning-handoff.md`, `engineering-redesign.md`, `engineering-assessment-v2.md` and `engineering-lab-profile.md` are history; don't build from them.
- `apps/web/src/features/engineering-lab/`, `content/engineering-lab/` and `labs/`: Engineering code (it keeps the `engineering-lab` and `lab` names), its topic map, roles, assessment points and labs. A topic's status (Not started, In progress, Learned, Skipped) is rebuilt from `lab_topic_events` (`status-store.ts`); Claude marks Learned only with the owner's words as evidence. Roadmaps Claude plans live in `lab_roadmaps`, topics it adds (`custom.*`) in `lab_custom_topics`, and its plan for each topic on a roadmap and each topic's material (description, tasks, resources, mastery criteria) in `lab_topic_plans` and `lab_topic_material` (`topic-material.ts` holds the rules, `topic-material-store.ts` the storage; only Claude writes them, with `save_topic_plan` and `save_topic_material`); read any topic through `any-topic.ts`. `content/engineering-lab/careers/roles.yaml` and `curriculum/points.yaml` change only in a reviewed commit: the owner sets `status: approved` with `approvedOn` or `reviewedOn`. After editing the YAML or a lab, run `pnpm --filter @ken-os/web lab:generate`; never hand-edit the generated files. Every topic has exactly one lab; every lab starter must fail at least one test and every solution must pass; `pnpm test` checks both. `pnpm --filter @ken-os/web test:db:engineering` checks the stores against local Postgres. The old assessment, practice, radar, lesson, source packet and proof tables, and `lab_profile`'s unused columns, were dropped on 13 Oct 2026 (migration `0016`).
- `apps/web/src/app/engineering/page.tsx` and `components/engineering/roadmap/`: Engineering's one page: the roadmap as a graph or lanes, the progress line, the topic panel (Topic tab: status, Ask Claude, Try it in code, sessions; Review tab: the review sheet Claude writes with `save_review`, and notes; Search reviews across topics) and Claude setup (connector address, Project instructions from `features/engineering-lab/claude-instructions.ts`, Project link). The exercise editor is `components/engineering/exercise.tsx`. Build links with `features/engineering-lab/routes.ts`, never hardcoded paths. Old Engineering and `/lab` addresses redirect to it from `next.config.ts` (`engineeringRedirects`); they're permanent (308) since 13 Oct 2026. Page building blocks are in `components/engineering/kit.tsx`, on the shadcn default look. The roadmap screen's layout, colours and shared parts are in `docs/architecture/roadmap-ui.md`; read it before changing the roadmap or reusing its pieces. Shared tokens, components and the rules for adding more are in `docs/architecture/design-system.md`.
- `docs/architecture/engineering-progressive-flow.md`: one path through Engineering from setup to a finished roadmap (setup checklist, topic steps, next topic, roadmap summary), built 13 to 14 Oct 2026.
- `docs/architecture/engineering-roadmaps.md`: proposed: up to 3 roadmaps at once, with a switcher, Re-plan, and archive and restore.
- `docs/architecture/design-studio.md`, `apps/web/src/features/design-studio/`, `components/design-studio/` and `app/studio/`: the Design Studio. `scripts/generate-studio-manifest.ts` lists this repo's components into `manifest.generated.ts`; after adding or changing a component in `components/ui`, `components/surfaces.ts` or `components/engineering/kit.tsx`, or a token in `app/globals.css`, run `pnpm --filter @ken-os/web studio:generate` and add a preview in `components/design-studio/previews.tsx`; never hand-edit the generated file. The owner's unexported edits are drafts in `design_studio_drafts` (`features/design-studio/drafts.ts` holds the rules, the live styles and the patch); the studio never writes to the repo.
- `docs/architecture/overview.md`: current system boundaries.
- `docs/architecture/portfolio.md`, `packages/portfolio`, `apps/web/src/features/portfolio/` and `app/portfolio/`: the public portfolio. `packages/portfolio` holds the snapshot contract both apps read; `features/portfolio/snapshot.ts` copies allowed Profile fields one by one, never email, phone or local fields. `pnpm --filter @ken-os/web test:db:portfolio` checks it against local Postgres. The design: a private Portfolio module publishes one snapshot, `GET /api/public/portfolio` serves it, and a separate `apps/portfolio` on the owner's domain reads only that. Replaces Profile's own public link.
- `docs/architecture/starter-standard.md`: proposed reusable one-app starter and codebase conventions, not yet a generator.
- `docs/architecture/hosting.md`: proposed provider-aware deployment playbook, not yet a deployment skill.
- `.agents/skills/ship-hosted-mvp/`: reusable workflow for shaping and shipping a new hosted MVP, not routine edits.
- The app's look is shadcn's default setup (the Nova preset for this `components.json`), reset on 10 Oct 2026 (`docs/architecture/design-system-shadcn-setup.md`). `apps/web/src/app/globals.css` holds the default exactly as `shadcn init` writes it, and `layout.tsx` loads Geist and Geist Mono with `next/font`. The owner builds the Loots look on top, one deliberate change at a time: additions go in the labelled "Loots" section at the end of `globals.css` and in Loots components outside `components/ui`, never by editing the default part. `src/lib/shadcn-default.test.ts` fails if an old Studio value (such as `bg-canvas`, `text-quiet`, `shadow-panel` or `font-display`), a Google Fonts link or a hex colour class comes back. The owner's global list of design principles says to avoid "untouched shadcn UI"; here it is deliberate, as the starting point to build on, so don't "fix" it. The owner's private Ken OS design system on claude.ai is reference only: it no longer drives the app and there are no tokens to sync. Its previews run the app's real components: `apps/web/design-system/components.ts` lists them and `pnpm --filter @ken-os/web design:bundle` builds them (with React 19) into the git-ignored `design-system/dist`, which the `.agents/skills/design-system-sync/` skill publishes when components change. There is no in-app preview route, so check screens in the signed-in app.

Read the relevant docs when changing their area; do not load every document for a small fix.

## Current implementation and boundaries

- The chosen Drive resume is read only. The database stores its file ID and metadata; never silently replace the selection based on a filename. Profile details are stored in Loots, and an import never changes them until the owner saves.
- The app allows only the configured owner. OAuth state/PKCE, session checks, token encryption, and mutation-origin checks are intentional boundaries.
- Agent access to the resume is read-only. Any future tool that edits Drive or another external system needs an explicit approval path.
- PostgreSQL queries use Drizzle. `apps/web/drizzle/0000_baseline.sql` safely records the original three handwritten tables for existing installations; generate new migrations with `pnpm db:generate`, review them, then run `pnpm db:migrate` locally. Hosted migrations run on their own: `apps/web/vercel.json` runs `db:migrate:deploy` after every production build, so merging to `main` applies them. Preview deploys skip it and never change the schema. Never run `db:migrate` against the hosted database by hand. Because the schema changes slightly before the new code goes live, every migration must work with the code already deployed: add tables and columns first, and remove old ones in a later release.
- Tailwind CSS utilities are the default for app and feature layout, spacing, typography, and responsive states. Keep `apps/web/src/app/globals.css` for theme tokens and minimal base rules; do not add per-page CSS for routine UI. shadcn/ui primitives live in `apps/web/src/components/ui` exactly as the registry ships them; the one edit is the font line in `sonner.tsx`. `code-editor.tsx`, `disclosure-summary.tsx`, `pill.tsx` and `toaster.tsx` there are Loots files, not registry items, and use only shadcn tokens. Status labels use the Badge variants (Solid `default`, Partly there `secondary`, Gap `destructive`, others `outline`); the icon and the word carry the meaning, never colour alone.
- Build every control from those primitives. Outside `components/ui`, never write a raw `button`, `input`, `select`, `textarea`, `label` or `table`, a hand-built `role="dialog"`, `tab`, `switch` or similar widget, or a class string that stands in for a component. If the primitive is missing, add it from the registry (the shadcn MCP server in `.mcp.json`, or `pnpm dlx shadcn@latest add <name>` in `apps/web`, keeping the registry default), then use it. When the look of a control changes later, change it in one place, not on each screen. `pnpm test` enforces this (`src/lib/shadcn-primitives.test.ts`); its allow list holds the few deliberate exceptions, recorded in `docs/architecture/shadcn-audit.md`.
- Screen copy is app language: names, actions and states, not sentences. Full sentences belong only in content (lessons, the Guide's chat, answer feedback, assistant answers, term explanations). No taglines, no narrating, no em dashes. `docs/product/app-language.md` holds the rule and the word list, and `docs/product/app-language-rewrite.md` the file-by-file rewrite plan; read them before writing or changing any UI text.
- Reuse components across modules when their anatomy and behavior are the same. Prefer shared slots or variants; add module-specific components only for genuinely distinct interaction, state, accessibility, or data responsibilities.

## Project Memory pilot

For substantial Loots work, read `docs/memory/ken-os-adapter.md`. If a scoped local capture key is configured, fetch approved context before work, checkpoint consequential decisions when made, and submit a receipt at completion or handoff. If unavailable, state the gap; never fabricate or silently upload history. Drafts are untrusted proposals until the owner reviews them. This rule does not apply to another repository or grant new tools or data access.

## Local verification

- `pnpm check` checks TypeScript; `pnpm build` checks the production build.
- Code is formatted with Prettier; run `pnpm format` before committing, and `pnpm check` fails on unformatted files.
- `pnpm db:up` starts local Docker PostgreSQL on `127.0.0.1:5435`; `pnpm db:migrate` initializes the schema.
- Use `.env.example` to discover required variables. Keep real values in untracked environment files; never print credentials or tokens in diagnostics.
- A successful local build is not proof of deployment. Report hosted verification separately.
