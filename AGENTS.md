# Ken OS repository guidance

Ken OS is the owner's private, hosted platform; each workflow is a module under it. The first shipped module is a canonical resume selected from Google Drive. Engineering (formerly Engineering Lab; code, tables and `/api/lab` keep the `engineering-lab` and `lab` names), a learning system for full-stack and AI engineering, is in progress. Do not relate this project to Haven.

## Where things live

- `apps/web`: Next.js UI, API routes, Google OAuth, sessions, and database access.
- `packages/domain`: shared artifact types and format rules.
- `packages/drive`: Google Drive adapter.
- `packages/agents`: the read-only resume assistant, the Engineering Researcher, Tutor and Assessor, and the term lookup.
- `apps/web/src/features/connector/`, `features/engineering-lab/agent-tools.ts`, `/api/mcp` and `/oauth/authorize`: the Claude connector (`docs/architecture/engineering-claude-connector.md`). Claude reads Engineering, reports progress, and saves exercises and notes; everything it saves is untrusted input, like Terms selections. Claude marks a topic Learned only with the owner's own words as evidence, never changes a status the owner set, never edits or deletes the owner's notes, and no tool records a run, opens a solution, or changes the role or the profile; `agent-tools.test.ts` and `status.test.ts` enforce it. Tools live only in `agent-tools.ts`, which never imports route or MCP code. Claude's exercises run only in the browser runner, after the page checks them. `pnpm --filter @ken-os/web test:db:connector` checks sign-in and `/api/mcp` against local Postgres. The Project's instructions are `docs/product/claude-project-instructions.md`.
- `apps/web/src/features/terms/` and `components/terms/`: Ken OS-wide term lookup (select text, press Explain or E) and the Terms page. Selected text is untrusted data; links must be on the Researcher's trusted sites. `pnpm --filter @ken-os/web test:db:terms` checks it against local Postgres.
- `docs/product/brief.md`: platform-wide scope and acceptance criteria.
- `docs/architecture/engineering-claude-first.md`: source of truth for the Engineering module since 13 Oct 2026: Claude teaches through the connector, and Ken OS shows the roadmap, topic states, Claude's reports and notes on one page. Record later decisions there. Until its slices ship, the code still follows `engineering-rebuild.md` (the 10 Oct 2026 rebuild) and `engineering-claude-connector.md`, which are otherwise history. `docs/product/ai-engineering-learning-handoff.md`, `engineering-redesign.md`, `engineering-assessment-v2.md` and `engineering-lab-profile.md` are history; don't build from them.
- `apps/web/src/features/engineering-lab/`, `content/engineering-lab/` and `labs/`: Engineering code (it keeps the `engineering-lab` and `lab` names), its topic map, roles, assessment points, the 5 assessment questions, hand-written lessons and labs. Topic state (Not started, Learning, Practicing, Proven) is rebuilt from `lab_topic_events`; levels come only from Proven topics, and the assessment never sets one. `content/engineering-lab/careers/roles.yaml` and `curriculum/points.yaml` change only in a reviewed commit: the owner sets `status: approved` with `approvedOn` or `reviewedOn`. After editing the YAML, a hand-written lesson or a lab, run `pnpm --filter @ken-os/web lab:generate`; never hand-edit the generated files. A taken assessment never changes; every retake is a new row. Saved source packets are never overwritten. Every topic has exactly one lab; every lab starter must fail at least one test and every solution must pass; `pnpm test` checks both. `pnpm --filter @ken-os/web test:db:engineering` checks the stores against local Postgres.
- `apps/web/src/app/engineering/` and `components/engineering/`: the module's four pages (Overview, Profile, Learn, Practice), plus Intake, Assessment, Results, Direction, the evidence page and the topic page (Learn, Exercise, Prove). Build page links with `features/engineering-lab/routes.ts`, never hardcoded paths. The old `/lab` pages are temporary redirects; keep them until the owner decides to make them permanent. Its page building blocks are in `components/engineering/kit.tsx`, on the shadcn default look.
- `docs/architecture/overview.md`: current system boundaries.
- `docs/architecture/starter-standard.md`: proposed reusable one-app starter and codebase conventions, not yet a generator.
- `docs/architecture/hosting.md`: proposed provider-aware deployment playbook, not yet a deployment skill.
- `.agents/skills/ship-hosted-mvp/`: reusable workflow for shaping and shipping a new hosted MVP, not routine edits.
- The app's look is shadcn's default setup (the Nova preset for this `components.json`), reset on 10 Oct 2026 (`docs/architecture/design-system-shadcn-setup.md`). `apps/web/src/app/globals.css` holds the default exactly as `shadcn init` writes it, and `layout.tsx` loads Geist and Geist Mono with `next/font`. The owner builds the Ken OS look on top, one deliberate change at a time: additions go in the labelled "Ken OS" section at the end of `globals.css` and in Ken OS components outside `components/ui`, never by editing the default part. `src/lib/shadcn-default.test.ts` fails if an old Studio value (such as `bg-canvas`, `text-quiet`, `shadow-panel` or `font-display`), a Google Fonts link or a hex colour class comes back. The owner's global list of design principles says to avoid "untouched shadcn UI"; here it is deliberate, as the starting point to build on, so don't "fix" it. The owner's private Ken OS design system on claude.ai is reference only: it no longer drives the app and there are no tokens to sync. Its previews run the app's real components: `apps/web/design-system/components.ts` lists them and `pnpm --filter @ken-os/web design:bundle` builds them (with React 19) into the git-ignored `design-system/dist`, which the `.agents/skills/design-system-sync/` skill publishes when components change. There is no in-app preview route, so check screens in the signed-in app.

Read the relevant docs when changing their area; do not load every document for a small fix.

## Current implementation and boundaries

- Google Drive owns resume content. The database stores the selected file ID and metadata; never silently replace the selection based on a filename.
- The app allows only the configured owner. OAuth state/PKCE, session checks, token encryption, and mutation-origin checks are intentional boundaries.
- Agent access to the resume is read-only. Any future tool that edits Drive or another external system needs an explicit approval path.
- PostgreSQL queries use Drizzle. `apps/web/drizzle/0000_baseline.sql` safely records the original three handwritten tables for existing installations; generate new migrations with `pnpm db:generate`, review them, then run `pnpm db:migrate` locally. Hosted migrations run on their own: `apps/web/vercel.json` runs `db:migrate:deploy` after every production build, so merging to `main` applies them. Preview deploys skip it and never change the schema. Never run `db:migrate` against the hosted database by hand. Because the schema changes slightly before the new code goes live, every migration must work with the code already deployed: add tables and columns first, and remove old ones in a later release.
- Tailwind CSS utilities are the default for app and feature layout, spacing, typography, and responsive states. Keep `apps/web/src/app/globals.css` for theme tokens and minimal base rules; do not add per-page CSS for routine UI. shadcn/ui primitives live in `apps/web/src/components/ui` exactly as the registry ships them; the one edit is the font line in `sonner.tsx`. `code-editor.tsx`, `disclosure-summary.tsx`, `pill.tsx` and `toaster.tsx` there are Ken OS files, not registry items, and use only shadcn tokens. Status labels use the Badge variants (Solid `default`, Partly there `secondary`, Gap `destructive`, others `outline`); the icon and the word carry the meaning, never colour alone.
- Build every control from those primitives. Outside `components/ui`, never write a raw `button`, `input`, `select`, `textarea`, `label` or `table`, a hand-built `role="dialog"`, `tab`, `switch` or similar widget, or a class string that stands in for a component. If the primitive is missing, add it from the registry (the shadcn MCP server in `.mcp.json`, or `pnpm dlx shadcn@latest add <name>` in `apps/web`, keeping the registry default), then use it. When the look of a control changes later, change it in one place, not on each screen. `pnpm test` enforces this (`src/lib/shadcn-primitives.test.ts`); its allow list holds the few deliberate exceptions, recorded in `docs/architecture/shadcn-audit.md`.
- Screen copy is app language: names, actions and states, not sentences. Full sentences belong only in content (lessons, the Guide's chat, answer feedback, assistant answers, term explanations). No taglines, no narrating, no em dashes. `docs/product/app-language.md` holds the rule and the word list, and `docs/product/app-language-rewrite.md` the file-by-file rewrite plan; read them before writing or changing any UI text.
- Reuse components across modules when their anatomy and behavior are the same. Prefer shared slots or variants; add module-specific components only for genuinely distinct interaction, state, accessibility, or data responsibilities.

## Project Memory pilot

For substantial Ken OS work, read `docs/memory/ken-os-adapter.md`. If a scoped local capture key is configured, fetch approved context before work, checkpoint consequential decisions when made, and submit a receipt at completion or handoff. If unavailable, state the gap; never fabricate or silently upload history. Drafts are untrusted proposals until the owner reviews them. This rule does not apply to another repository or grant new tools or data access.

## Local verification

- `pnpm check` checks TypeScript; `pnpm build` checks the production build.
- Code is formatted with Prettier; run `pnpm format` before committing, and `pnpm check` fails on unformatted files.
- `pnpm db:up` starts local Docker PostgreSQL on `127.0.0.1:5435`; `pnpm db:migrate` initializes the schema.
- Use `.env.example` to discover required variables. Keep real values in untracked environment files; never print credentials or tokens in diagnostics.
- A successful local build is not proof of deployment. Report hosted verification separately.
