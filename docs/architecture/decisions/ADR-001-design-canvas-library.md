# ADR-001: Design canvas library — adapt React Flow, don't adopt a new framework

**Status**: Proposed

**Date**: 2026-10-31

**Decision Makers**: the owner

**Tags**: design-canvas, react-flow, mockups, design-tooling

Superseded in scope on 31 Oct 2026: this started as a feature proposal inside Design Studio. The owner has since
decided it is its own product, **Design** (see [design.md](design.md)), built from the ground up rather than layered
onto Design Studio's existing code. The library research and conclusion below are unchanged and now apply to Design
instead.

- **Accepted or rejected by/date:** _blank until the owner acts_
- **Scope and expected lifetime:** the canvas library behind Design (`apps/web/src/features/design`,
  `apps/web/src/components/design`), expected to carry mockup work for as long as Loots keeps drawing its own screens
- **Confidence:** high, on eliminating every external framework candidate; medium, on the exact shape of the "Frame" mechanism until it's built

## Job and outcomes

Loots currently draws UI mockups (see `docs/mockups/job-finder.md`, `docs/mockups/design-studio.md`) using the Figma MCP server and the Paper MCP server. Both gate and rate-limit access, which blocks the mockup workflow. The job: add a lightweight, self-hosted way to compose named frames at fixed sizes (desktop 1440x900, phone 390 wide) from real Loots/shadcn components, with a shared color/token reference, editable both by Claude Code (programmatically) and by the owner (by hand, dragging and resizing), without owning a second design-tool framework alongside the one already built for Design Studio.

Scope is trimmed to only what the existing mockup briefs actually use: named frames, real components (not vector shapes), text edits, a shared token reference, and a screenshot review step. Out of scope: multiplayer collaboration, FigJam-style diagramming, and anything beyond the Code-Connect-style design-to-code mapping Design Studio already does.

## Local capabilities inspected

- **Existing repository capability:** `@xyflow/react` (React Flow) v12.12.0 is already a dependency. `apps/web/src/components/design-studio/studio-graph.tsx` already renders every installed component live as a custom React Flow node (`ComponentNode`), with real pan/zoom/select, inside a `ReactFlowProvider`. Every node is currently `draggable: false` and `selectable` with auto-computed positions from `layoutGraph` in `apps/web/src/features/design-studio/manifest.ts` — the canvas is a read-only, auto-laid-out dependency graph today, not a freeform editor, so dragging/resizing/grouping exist in the library but are unused in this codebase.
- **Existing repository capability:** `apps/web/src/features/design-studio/drafts.ts` already has a proven pattern for this exact job: a typed, server-validated draft (`parseDraft`), live re-render with no save round trip, a Postgres `design_studio_drafts` table, and an export path that turns a draft into a real code diff (`draftPatch`, "Copy as patch"). A new "placed component" draft kind can reuse this pattern directly instead of inventing a new persistence model.
- **Existing repository capability:** `.claude/skills/impeccable/scripts/live-browser.js` and `modern-screenshot.umd.js` already give the agent a live-browser screenshot path. This is harness/skill tooling, not an `apps/web` dependency, so the "review via screenshot" need is already met without adding anything to the app.
- **Standard library / open standard:** none applicable; this is a UI composition problem, not a protocol or data-format problem.
- **Framework, runtime, platform, browser, database, or OS primitive:** the app is a Next.js/React 19 app; no platform-level canvas primitive fits better than a library choice here.
- **Existing supported dependency/tool:** React Flow (above) is the only existing dependency that's a credible fit; no other canvas/whiteboard/drag-drop package is in `apps/web/package.json` today.

## Decision

- **Outcome:** adapt
- **Recommendation:** build Design on top of `@xyflow/react` (React Flow), already a dependency of this repo, instead of adopting any new framework. A `Frame` node type (named, fixed-size via `<NodeResizer />`, e.g. "Desktop / New" at 1440x900) holds `PlacedComponent` nodes, draggable and resizable using `parentId` + `extent: "parent"`. Placements persist through a validated-draft pattern of Design's own (same shape as Design Studio's `drafts.ts` proves out for a different job: validate, persist, live re-render, no save round trip), reached through Design's own API route. Claude Code edits the same placements programmatically; the owner edits them by dragging in the browser. Review stays outside the app, using the agent's existing live-browser screenshot tooling.
- **Why this wins:** every external framework candidate fails a hard gate (tldraw: cost/license; Excalidraw and Konva: can't host live interactive components; GrapesJS: the capability that matters is paywalled or unverified) or loses on current, dated maintenance evidence against a zero-new-dependency alternative that already clears every gate (Craft.js, react-moveable/react-selecto). React Flow is already trusted, already MIT, already doing the closest-possible job elsewhere in this repo (Design Studio's dependency graph), and its parent/child grouping and resize features are native, documented, and current.
- **Strongest counterargument:** React Flow's node model was designed for graphs, not free-form page composition; a purpose-built page-builder (if one existed with a clean license, native React rendering, and healthy maintenance) would likely need less custom "Frame" plumbing than bolting grouping/resize semantics onto a graph library. No such candidate survived the hard gates today, but this gap is real and worth re-checking as the ecosystem moves.
- **What bespoke glue or ownership remains:** the `Frame` node type, turning on drag/resize/grouping (React Flow ships it, but nothing in this repo has switched it on yet), and a new validated-draft/placement model and its export logic, built fresh for Design rather than inherited from Design Studio.
- **What evidence would change the decision:** a credible, actively maintained, MIT/BSD-or-equivalent-licensed library emerges that natively mounts real React component trees inside a freeform, resizable canvas with no commercial gate — none of today's candidates meet that bar.

This remains a proposal until the owner records acceptance.

## Proof of fit

- **Question and representative workload:** can a `Frame` node (1440x900), containing 3 to 5 real live components dragged and resized by hand, round-trip through Design's placements table and re-render correctly in both light and dark theme?
- **Success/failure boundary:** a dragged/resized placement persists across a refresh, re-renders the real component (not a stale snapshot), and validates against Design's own catalogue the same way Design Studio's `parseDraft` already does for tokens and Look edits.
- **Execution authority:** the owner, once Design's first build step is scoped as its own PR, per `design.md`.
- **Exact artifact/version and checksum/signature/provenance:** no new package; `@xyflow/react` stays pinned at the version already in `apps/web/package.json`.
- **Least-privilege sandbox:** none needed — this is new code in a new module, not an external package trial.
- **Network, mounts, credentials, host services, and other authorized exceptions:** none.
- **Timebox:** sized as one PR-sized build step, matching Design Studio's existing build-order convention.
- **Result or unresolved obligation:** not yet attempted; this decision document is the gate before that PR is scoped.

## Ownership and implementation route

- **Upgrade/security/incident owner:** whoever already owns `apps/web`'s dependency upgrades; no new owner needed since no new dependency is added.
- **Supported version/range or service tier:** `@xyflow/react` ^12.12.0, matching the existing pin.
- **Dependency boundary:** Design's `Frame` node type and placement logic live in their own module, `apps/web/src/features/design` and `apps/web/src/components/design`, independent of Design Studio's files.
- **Rollout and recovery:** ship as its own PR per `design.md`'s build order; rollback is deleting Design's module, since it shares no code with Design Studio.
- **Implementation skills/plan:** route through `codebase-design` for the `Frame` node type's contract, `tdd`/`testing` for the placement validation and export logic, and `planning` to sequence it as its own build step once the owner accepts this decision.

## Exit and re-evaluation

- **Data/configuration export and replacement path:** placements are plain JSON rows in Postgres, in Design's own table; exporting or dropping the feature doesn't touch Design Studio's drafts or tables.
- **Removal/migration cost:** low — delete Design's module and its tables; `@xyflow/react` stays in use for Design Studio's graph regardless.
- **Re-evaluate when:** a maintained, commercially-unencumbered library emerges that natively hosts live React components in a freeform canvas; or React Flow's grouping/resize behavior proves too graph-shaped once real mockup work is attempted (see Proof of fit).
